01
DBSCAN clustering — 10,000 alerts → 50 incidents
Consumes every finding.created Kafka event from CSPM, CWPP, CIEM, KSPM, CDR, and CI/CD. Groups findings by feature vector: same resource_type + rule_category + account + environment = same cluster. Each cluster is promoted to a single incident, not N individual alerts. Keeps SOC teams focused on real threats, not noise.

False positive suppression model — XGBoost classifier
Gradient boosting classifier trained on historical user feedback. Features: rule_id, resource_type, account, environment, time_of_day, tags. Label: finding was resolved as false_positive. Auto-suppresses findings above configurable probability threshold. Retrained weekly on accumulated feedback. Gets smarter the more customers use it.

Attack path analysis & blast radius
03
Graph-based attack path computation — Neo4j BFS traversal
Runs every hour and on significant graph changes. Identifies all internet-accessible entry points in the asset graph (public IPs, public S3, public ALBs). From each entry point, runs BFS up to 8 hops. Looks for paths that reach crown-jewel assets: production databases, Secrets Manager, assets tagged criticality=high, assets containing PII. Scores paths: fewer hops + more misconfigs + more sensitive target = higher risk.

"What-if" blast radius simulation
Given any resource ID, show every attack path that passes through it. If this S3 bucket is breached, what data stores and systems are reachable? If this IAM role is compromised, what can the attacker assume next? Used during incident response and during planning for remediation prioritization.
Attack paths chain misconfigurations (CSPM) + vulnerabilities (CWPP) + IAM gaps (CIEM) into complete compromise scenarios — something no individual module can do alone. This is the power of the unified asset graph.

05
LLM-generated fix code with PR auto-open
When a finding has auto_fix_available: true in its Rego rule metadata, the system prompts Claude as a cloud security remediation specialist. It outputs only directly applicable code — Terraform HCL, IAM policy JSON, Kubernetes YAML, or CLI commands — never invented configurations. For IaC findings, the service opens a PR against the customer's GitHub or GitLab repo with the fix pre-applied. Tracks: PR opened → merged → finding resolved.

How AIOps enhances each pipeline stage
The CI/CD module produces findings at every stage. AIOps subscribes to those findings via Kafka and: (1) applies the Priority Score model to rank them by exploitability before surfacing them to developers, (2) suppresses known false positives using the trained XGBoost model, (3) correlates pipeline findings with runtime posture to show which code-level issues are already exposed in production, (4) generates auto-fix PRs via Claude for any finding with auto_fix_available=true, and (5) feeds new signals back into behavioral baselines for CDR.

Developer feedback loop — what AIOps delivers to devs
PR
Inline PR annotations ranked by AIOps priority score — critical exploitable issues flagged at the top, known false positives suppressed. Developers see signal, not noise.
FX
AI-generated auto-fix PRs for IaC findings — Terraform blocks, IAM policies, Dockerfile patches — opened automatically against the source branch. Developer approves, AI does the grunt work.
🔌
IDE plugin (VS Code, JetBrains) with pre-commit security checks. AIOps-scored severity surfaced inline — no context switching required. Catches secrets, IaC misconfigs, and vulnerable deps before the first commit.
TK
Jira / Slack auto-ticket creation on pipeline gate failure. Ticket includes: finding detail, AIOps priority score, suggested fix, linked runtime exposure status (is this already live in prod?), and one-click copilot link.
RM
Copilot-generated incident postmortem drafts — traces the incident back to the source PR, identifies the gap in the pipeline gate that allowed it to ship, and suggests the policy rule change to prevent recurrence.
→
Policy enforcement gates — 3 modes
Advisory (warn)
Finding surfaced to developer. Pipeline continues. AIOps score shown. Good for onboarding — builds awareness without blocking teams.
Soft gate (override)
Pipeline pauses on findings above AIOps threshold. Developer can override with reason. Override is logged and audited. Good for teams that need velocity.
Hard gate (block)
Pipeline fully blocked on critical findings. No override. Only security team can unblock. Good for prod pipelines after a team has matured.

CDR — cloud detection & response (AIOps runtime layer)
CDR
MITRE ATT&CK threat detection — real-time
CDR is the runtime expression of AIOps. It ingests CloudTrail, Azure Monitor, GCP Audit Logs, Kubernetes audit logs, VPC Flow Logs, and eBPF runtime events. UEBA baselines (built by the aiops service) are evaluated against every new log event to detect deviations. Pre-built detections cover all MITRE ATT&CK Cloud Matrix tactics.

Automated response playbooks (require human approval by default)
Compromised IAM user → revoke all active sessions + disable access key + enforce MFA reset. Compromised EC2 → isolate via security group + create forensic snapshot. Data exfiltration → revoke IAM role + block source IP in WAF. Crypto miner → terminate instance + create forensic snapshot first. All playbook steps are logged for compliance.
