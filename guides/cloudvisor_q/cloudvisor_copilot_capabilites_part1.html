What the Copilot service does

The Copilot service provides a natural-language interface to every data source in CloudVisor. Users — security engineers, SOC analysts, CISOs, compliance officers — can ask questions in plain English and receive grounded, cited answers drawn from live data: the asset graph, open findings, compliance posture, audit trail, and historical snapshots. It does not replace the dashboard; it provides a second, conversational layer on top of it for tasks that are too complex or too ad-hoc to express as filters.

The service is read-only and tenant-scoped. Every retrieval step enforces PostgreSQL Row-Level Security and the RLS session context, so the LLM can only see data belonging to the requesting organization.
⚙️

6-step RAG pipeline

1
Intent classification in-process
The user's query is classified into one of 7 intents (POSTURE, FINDING, COMPLIANCE, REMEDIATION, THREAT, DRIFT, GENERAL) to determine which retrieval sources to activate and how to weight them in the final prompt.
2
Semantic embedding stub — to implement
The query is embedded using a text embedding model. The resulting vector is used to retrieve semantically similar findings and assets from the vector store. (Step currently commented out — pending vector store integration.)
3
Multi-source retrieval live
Based on intent, relevant data is fetched in parallel from: asset graph (Graph Service API / Cypher), findings (Alert Service API / Elasticsearch), compliance posture (Policy Service API), audit log, and CSPM snapshots. All queries are tenant-scoped via RLS.
4
Prompt construction live
A structured prompt is assembled: system role definition + retrieved context blocks (findings, assets, compliance data, audit events) + the user's original question. Context is formatted for clarity and trimmed to fit the model's context window.
5
LLM call via provider factory live
The constructed prompt is sent to the configured LLM provider. Primary is Anthropic Claude (claude-sonnet-4-6). Fallbacks are Google Gemini (flash-lite), OpenRouter (gemma-4-31b-it), and local Ollama (qwen2.5). Provider is selected via COPILOT_LLM_PROVIDER env var.
6
Response parsing + audit logging partial
The LLM response is parsed to extract structured citations (finding IDs, asset IDs, rule IDs). The full query + response is written to copilot_queries (append-only audit log) and a copilot.query_logged Kafka event is emitted. Citation parsing currently returns an empty list — pending full implementation.

Auto-remediation (REMEDIATION intent)

When a finding has auto_fix_available: true in its rule metadata, the copilot can generate a ready-to-apply fix. The LLM is prompted as a cloud security remediation specialist and constrained to output only valid, directly applicable code — Terraform HCL, IAM policy JSON, Kubernetes YAML, or a CLI command sequence. It also explains why the fix addresses the root issue.

For IaC findings (Terraform / Helm), the service can open a pull request against the customer's Git repository via GitHub or GitLab API, with the fix pre-applied. The platform tracks: PR opened → PR merged → finding resolved.
Terraform HCL IAM policy JSON Kubernetes YAML CLI commands GitHub PR auto-open GitLab MR auto-open

Security model

The copilot is strictly read-only — it can never trigger destructive operations. All data retrieval runs under an active RLS session, meaning the LLM only ever receives data belonging to the requesting organization. Every query and response is written to the copilot_queries append-only audit table and emits a copilot.query_logged Kafka event. The audit log is retained and immutable — no deletes, no updates.
